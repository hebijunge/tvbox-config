# 核心需求五环评估报告（2026-09-28）

> 核心需求：**全网搜集可用 tvbox 点播/直播接口 → 汇总去重 → 依赖落库 → 生成可用配置**。
> 本报告按「搜集 / 验可用 / 去重 / 依赖落库 / 生成配置」五环逐环取证，给出问题清单与改法。
> 所有数字均取自当日仓内真实产物（status.json / exports / state / probe / 磁盘实测），非估算。

---

## 总评：一句话结论

**管道骨架完整、能跑通端到端，但当前产出的「可用配置」严重名不副实——3724 站里真正
实测可用的只有 127 站（3.4%），而配置里 40% 的本地依赖引用指向磁盘上不存在的文件，
意味着订阅用户导入 tvbox.json 后大量源是坏的。优先级最高的不是「再收更多源」，
而是「把已有源修到真的能用」。**

| 环 | 现状健康度 | 最高优先级问题 |
|---|---|---|
| ① 全网搜集 | 🟡 能收但漏收 | 候选池 7 天未更新；6 路里 Gitee 路实质失效；issue 自动收录停在 9-21 |
| ② 验可用 | 🔴 覆盖率低 | 3724 站中 2396 站 unknown（64% 未实测）；直播 432 条仅 19 条 healthy |
| ③ 去重 | 🟢 基本扎实 | api+ext 全同重复仅 1 组（二级去重有效）；同 api 多 key 是**不同配置不是重复**，勿误删 |
| ④ 依赖落库 | 🔴 最致命 | **40.3% 的 deps/ 引用磁盘缺失（771/1912），681 个站受影响**；drpy2.min.js 引擎 307 处缺失 |
| ⑤ 生成配置 | 🟡 产物分层好但有坑 | tvbox.json 无健康标注（0/3724）；根 live.json 是 1 条指针（设计如此但易误用） |

## 环① 全网搜集

**数据**：radar/discovered 80 候选；candidate_eval（9-28）fetch_ok 30 / with_unique 27 / 总新增站 1872；
candidate_upstreams.json 停在 9-21（2 候选）；canary `auto/` 系列 9-28 正常。

**问题**：
1. **候选池停滞 7 天**：`radar.yml` 周一 11:00 跑，但 `candidate_upstreams.json`（issue→PR 人工池）
   停在 9-21，6 天无人确认收编——自动发现能跟上，人工收编是断点。
2. **Gitee 路实质失效**：README 自己写明 Gitee 搜索 API 被禁、网页 WAF 405，
   只能走「GitHub 搜引用 gitee 的配置」曲线，产出趋近 0，占六路之一但近乎空转。
3. **发现→可用闭环太长**：发现 80 候选 → 评估 → canary 收编 → 实测 → 进主库，
   链路 4 步，中间 canary 池 9-28 才 5 个 `auto/` 源生效，从发现到「可用源」转化率低。

**改法**（按性价比）：
- P1：把 candidate_upstreams 的人工确认做成**每周固定提醒**（可挂 automation 或飞书待办），消除 6 天断点。
- P2：Gitee 路若 3 个周期内 unique=0，降级为可选路（省 token/时间），资源转投「血统反查」（产出最高）。

## 环② 验可用（当前最大短板）

**数据**：3724 站 → healthy 127 / degraded 659 / **unknown 2396（64%）** / dead 542。
探针覆盖：sites_probe 382、spider_probe 2861（连通）、js_probe 715、drpy_probe 379、
csp_probe **700（9-19，已 STALE>7 天被降权）**。

**问题**：
1. **unknown 占 64%，等于 3724 站里 6 成「可用性未知」就进了配置**——这是「生成可用配置」
   这个需求下最扎眼的问题：用户导入的是 unknown，不是「可用」。
2. **csp 真机探针 9-19 已 9 天未刷新**，被 `PROBE_STALE_DAYS=7` 降权，
   意味着 700 个 csp 源当前**全部不参与排序**，csp 源（占 87%）实际处于「无深结论」状态。
   （本轮 9-28 正在真机全量补测 962 个，见「进行中」。）
3. **直播 432 条仅 19 healthy / 15 degraded / 110 dead 实测**，`live.json` 仍打包 432 条含死源，
   无频道级验活（同一直播源内 100 个频道里死 80 个也照发）。

**改法**：
- P0（进行中）：真机补测 962 个 csp 源 → csp_probe 刷新到 9-28 → 解除 STALE 降权 → unknown 大幅下降。
- P1：把「unknown 占比」纳入 CI 健康门槛——unknown 超过阈值（如 40%）时 CI 出告警，
  防止「没测过的源静默进配置」。
- P1：直播源按**频道**验活（不只按源），dead 频道从 live.json 剔除或下沉。

## 环③ 去重

**数据**：二级去重（api+ext 全同）仅查出 **1 组 / 2 站**（csp_Zxzj），已清。
同 api 不同 key 有 2025 站（227 簇，如 csp_XBPQ 394 站），但**经实证 api+ext 全同的仅 1 组，
域名变体镜像估算 0**——说明这 2025 站是「同一个爬虫类挂不同配置/不同 ext 的不同站」，
**不是重复，不能删**。

**结论：去重环基本扎实，二级去重生效，无过度去重风险。**

**唯一要守住的坑**：
- ⚠️ 不要把「同 api 多 key」当重复误删——csp_XBPQ 394 站是 394 个**不同片库/不同 ext**，
  删了就丢源。去重判据必须锁定 api+ext 全同（现口径正确，保持）。

## 环④ 依赖落库（最致命，P0）

**数据（磁盘实测，非 state 报告）**：tvbox.json 内 1912 条 deps/ 引用，
**771 条（40.3%）指向磁盘上不存在的文件**，波及 **681 个站**。缺失 Top：
- `deps/auto/11-298s/.../drpy2.min.js` ×307 —— drpy 引擎缺失，这批本地 JS 源**全坏**
- `deps/sv/liucn-m/box/libs/js/drpy2.min.js` ×76
- `deps/sv/fongmi-z/z/json/peizhi.json` ×46
- `deps/qist/jsm/lib/drpy2.min.js` ×34

**问题**：
1. **40% 依赖缺失 = 配置里 4 成带本地依赖的源是坏的**。这直接击穿「生成可用配置」需求。
   根因：canary 收编 / 上游换路径后，deps 目录里的旧路径没同步，引用悬空。
2. deps/ 396MB / 3926 文件里有 **dead_dep_refs 729 个 api 端点未改写** + 大量 localized 死文件，
   体积虚胖且脏。

**改法**（P0，建议本轮就动手）：
- **依赖完整性闸门**：生成 tvbox.json 后跑一遍「引用→磁盘存在」校验，
  缺失的**自动重下**（collect_and_rewrite_deps 已有下载能力，补「校验发现缺失→补下」闭环）；
  下不来的（404）把该站**降级/剔除**，不让坏引用进发布产物。
- drpy2.min.js 这类**引擎级公共依赖**单独固化为一份（仓库根 `lib/drpy2.min.js`），
  所有 drpy 源引用指向它，消除 307+76+34 处各自缺失。
- deps/ 跑一次 dep_gc（已 dry-run 过）+ 清 729 死 api 引用，压体积。

## 环⑤ 生成配置

**数据**：产物分层清晰——tvbox.json（全量）/ vod.json / live.json / short.json /
exports/healthy.json（127 推荐）/ usable.json（786）。但：
- tvbox.json 站点**无健康标注**（0/3724 带 _health）——主配置是「裸站列表」，
  可用性信息只活在 exports/ 分层里，主配置读者拿不到「哪些真能用」。
- 根 `live.json` 只有 **1 条指针**（指向 lives/live_all.txt 聚合文件），
  exports/live.json 才是 432 条。设计如此（单仓单端点），但 README 顶部「live.json 订阅」
  给的是根指针，用户若期待 432 频道会困惑。

**改法**：
- P2：tvbox.json 站点补 `_health/_latency` 标注（export_healthy.enrich 已有逻辑，
  复用给主配置），让「主配置自带健康度」。
- P3：README 明确「根 live.json=单指针 / exports/live.json=全量 432」，消除误用。

## 推荐执行顺序（对齐你的核心需求）

1. **环④ 依赖完整性闸门（P0，最高优先）**——不修这个，前面收再多源都是坏配置。
   本轮就能做：缺失自动重下 + drpy 引擎固化 + 下不来的源降级。
2. **环② unknown 收敛（P0/P1）**——真机补测（进行中）+ CI unknown 占比告警 + 直播频道级验活。
3. **环① 候选池人工断点（P1）**——每周固定收编提醒，别让自动发现白收。
4. **环⑤ 主配置带健康度（P2）**——复用 enrich 逻辑给 tvbox.json。
5. **环③ 守住去重口径**——api+ext 全同才删，勿误删同 api 不同配置。

> 一句话排期建议：**先做环④（依赖闸门），同时等环②真机补测落地，两个合起来才真正
> 把「生成可用配置」做实；环①⑤ 是锦上添花，环③ 保持现状即可。**
