# searchable 字段细化方案

> 状态：待确认

## 背景与问题陈述

- TVBox 站点有 `searchable` 字段（0/1/2）：0=不可搜，1=可搜，2=仅聚合搜。
- 当前做法：要么直接信任上游自报的 `searchable`，要么简单探针打标。
- 问题：
  - 上游自报可搜但实际搜不动 → 误判。
  - 最近 3 天刚探过不可搜的源，会一直沉底，哪怕上游已修复。
  - 现有 `search_verdict` 是二值（可/不可），缺中间态。

## 方案设计

### 8.1 可搜内按命中数排序

对判定为"可搜"的源，再按探针实测命中数排序：
- 实测搜一个通用关键词（如"斗罗大陆"），返回结果数 N。
- N=0：实际不可搜，降级。
- 1 ≤ N < 5：弱可搜。
- N ≥ 5：强可搜。

排序时强可搜排前，弱可搜排后。

### 8.2 自报可搜但未实测 → 标记"待验证"

```python
if site.get("searchable") == 1 and not probe_result:
    site["search_verdict"] = "untested"
```

"待验证"的源不沉底但也不排前，tvbox.json 里仍保留 `searchable=1`（客户端兼容），但内部 state 记录待下次探针验证。

### 8.3 最近 3 天刚标记不可搜 → 不沉底

避免"上游偶发故障被永久判死"：
- 探针判定不可搜后，记录 `search_verdict_at` 时间戳。
- 3 天内重新探一次；若仍失败，才正式沉底。
- 3 天内的源排序权重不降到 0，保留 0.5 权重观察。

### 8.4 与现有 search_verdict 兼容性

| 现有值 | 新方案 |
| --- | --- |
| `"ok"` | 拆为 `"ok_strong"` / `"ok_weak"` |
| `"fail"` | 加时间戳，3 天内降权不沉底 |
| 无 verdict | 新增 `"untested"` 态 |

tvbox.json 输出层仍写 `searchable: 0/1/2`（客户端只认这个），细分状态只在 `state/search_verdicts.json` 里。

## 影响评估

| 面 | 影响 |
| --- | --- |
| tvbox.json 结构 | 不变（仍 searchable 字段） |
| CI 时长 | 多一轮搜索探针，预计 +1~2min |
| 用户体验 | 可搜的源真的能搜到，减少"点进去搜不到"的失望 |

## 实施步骤（分阶段可回滚）

1. **阶段 1**：写 `scripts/search_probe.py`，对每个可搜源实测一次，结果落 `state/search_verdicts.json`。
2. **阶段 2**：排序时引入 verdict 权重。
3. **阶段 3**：3 天重探窗口上线。

## 回滚方案

- `SEARCH_PROBE_DISABLED=1` 跳过搜索探针，回到仅信任自报。
- verdict 文件删除即回到旧逻辑。

## 需用户确认的决策点

1. 实测搜索关键词用哪个？固定一个通用词（如"斗罗大陆"）还是多词取平均？
2. 重探窗口 3 天是否合适？
3. "待验证"源是否在 tvbox.json 里保留 searchable=1，还是临时写 0？
